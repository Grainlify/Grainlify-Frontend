Projects apply to take part in a GrainHack event while it is in its **Application period**. Each application covers one repository. You accept or reject them, or ask for more information, in **Pending project applications** on the event's page in **GrainHack admin**.

## Open an application

1. **Open GrainHack admin, then the event.** On the **Hackathons** tab, choose the event from the list.
2. **Find Pending project applications.** It sits below the event form. Each row shows the repository and its short description. When there are none, it says **No pending applications.**
3. **Expand a row.** Choose the repository name or the arrow. The row opens to show the project's **Goal**, its **Expected issues** and the **Maintainer contact**, followed by the signals panel.

   ![A pending project application, expanded, with its auto-collected signals](shot:admin-gh-applications?desktop "Expanded application with signals")

## Read the signals

**Auto-collected signals** are gathered, mostly from GitHub, the first time you open an application. They help you judge whether the project is genuine and active. None of them decides anything on its own.

| Signal | What it tells you |
| --- | --- |
| **Repo created** | When the repository was created |
| **Had commits before announcement** | Whether it had any commits before the event was announced |
| **Commits (last 90 days)** | How active it has been recently |
| **Distinct contributors** | How many different people have contributed |
| **Prior GrainHack participation** | How many earlier GrainHack applications it has, or **None** |
| **Median time to first review** | How quickly maintainers usually start reviewing pull requests, in hours |
| **Prior flagged associations** | Not collected yet. It always shows a note saying it is not available. |

A signal that could not be worked out shows why, or **Not available**. Signals are kept for an hour. Choose the refresh icon, **Refresh signals**, to collect them again now.

## Decide

Use the icons at the end of the row.

| Action | What happens |
| --- | --- |
| **Accept** | The project is in. The applicant is notified that they can now label issues to enter them into the event. |
| **Request more info** | You write what is missing. The applicant is notified with your text, and the application leaves the pending list. |
| **Reject** | You write why. The applicant is notified with your text. |

For **Request more info** and **Reject**, a window opens with a **Reason** field. It is required, and the applicant reads it word for word, so be specific about what is missing or wrong. Then choose **Request info** or **Reject**.
